# 学习记录同步保护与恢复

## 2026-09-17 故障与处理

旧实现把整份本机快照的时间作为新旧依据。新设备改变年份或展开句子也可能获得更晚时间，从而跳过已有云端记录；随后无版本条件的 PUT 会覆盖整份云端数据。隔离测试复现了这条危险路径，但未读取真实账号，不能据此断言某个用户已丢失记录的具体内容和时间。

本次修复与数据恢复是两件事：保护未来写入不会自动找回此前已经被覆盖的内容。

## 同步规则与安全边界

- 登录、已有会话启动、断网重连都先 GET 账号快照。账号不一致、响应异常、读取失败或本机存储不可用时，不开放自动上传。
- 本机v2存储按邮箱分区，保存当前草稿和上次确认的云端基线。访客记录单独保存；无法确认所属账号的旧v1记录保持原样，不自动上传，不跨账号迁移。
- 合并比较“基线、本机、云端”，不比较设备墙钟。独立条目可合并；一端未修改则接受另一端的修改/删除；标签和清单成员合并且尊重基线删除。同一条目两端分别改写或一端删除另一端改写，会保留本机、另存安全副本并暂停上传。
- 冲突面板可“导出本机备份”，或显式选择“使用云端记录（本机另存备份）”。选择云端前必须成功保存本机副本。未处理冲突时可继续本机学习，不能把这种状态显示成云端已同步。
- 每次 PUT 同时携带 `accountEmail` 与 `expectedUpdatedAt`；服务端依据会话确定用户，用条件更新原子比较版本。并发写入至多一份成功；首次建行使用不覆盖插入。旧无版本客户端返回428，版本/账号冲突返回409，不改现有记录。
- PUT 必须同源、通过会话认证及结构/大小校验；已有实质记录不能被全空记录替换。整份清空属于被阻止操作，包括删除最后一项后上传；本次未新增危险的“一键清空”通道。
- 上传串行处理；请求期间新增的编辑仍保存在本机，并在确认上一版后继续发送。网络失败不假定云端未执行，而是暂停、再次读取后比较。
- 新旧协议都不存密码或Cookie到学习记录。本次没有调整密码算法、账号允许范围、域名、服务或部署目标。

## 写前备份与部署

`0002_study_state_backups.sql`增加 `study_state_backups` 和 `preserve_study_state` 触发器。每次有效更新前在同一SQLite语句事务内保存旧payload，备份失败使更新失败。保留每账号最近20个历史版本，另保留最近30天每天最早归档的检查点；这是有界回退记录，不保证每次击键的永久历史。检查点按UTC日归档。

既有main构建流程先幂等运行0001和0002，再发布Worker。其他CI、本机构建及预览分支不运行远端迁移；目标和权限检查不变。服务端检查触发器存在，缺失时拒绝上传。新增备份从安装后第一次更新开始，不能补造本次故障前的版本。

## 用户先做的保全

1. 若任何旧设备还显示原笔记，先断网，不清缓存、不卸载浏览器、不反复登录。
2. 更新后的账号面板点击“导出本机备份”。文件包含当前账号的草稿、同步基线、安全副本及本浏览器仍存在的旧v1原件；不导出其他已隔离账号的分区。文件可能含私人笔记，应保存到私人目录，不提交Git，不公开上传。
3. 本机存储区分浏览器、设备和站点来源；必须在原来使用的浏览器及域名查找。某台新设备空白不能证明旧设备或云端历史副本也不存在。
4. 确认当前登录的是需要恢复的账号后，可点击“恢复本机旧记录到当前账号”。只从本浏览器保留的旧v1原件合并，不删除当前新增记录；同条目有冲突时整次停止、双方原件不变。合并成功先保存本机，再按正常版本检查上传，须查看云端同步状态；此按钮不代表故障前数据一定仍在。
5. 若显示格式异常或空间不足，保留现场并导出；不要以清理localStorage作为修复方式。不自动导入来源不明的外部备份文件。

## 历史恢复流程（管理员操作，未自动执行）

优先恢复来源依次为：仍有原记录的本机/导出文件、修复上线后的账号历史快照、故障前Cloudflare D1 Time Travel恢复点。

2026-09-17查阅Cloudflare官方Time Travel文档：生产存储后端默认启用；Workers Free通常可回溯7天，Paid为30天，应核实实际计划与可用恢复点。原地Time Travel恢复是**全库破坏性回滚**，不是读取单个账号历史；官方当时仍说明不支持直接克隆某个恢复点为新库。

官方依据：
- https://developers.cloudflare.com/d1/reference/time-travel/
- https://developers.cloudflare.com/d1/platform/limits/

执行边界：

1. 先确认故障的大致时间与时区、需要恢复的范围；只由有权限的管理员检查恢复点元数据，不把账号、Cookie、令牌或生产数据库内容发到聊天或提交仓库。
2. 先保存当前库/当前账号的可恢复副本及当前Time Travel书签。**不能为单账号直接回滚整库**；这会同时回退其他人的新笔记、会话、密码和新增备份结构。
3. 如只剩全库历史恢复点，必须另行确认维护窗口、暂停写入、完整现状备份、回退验证及回到现状的方案，再由授权管理员恢复历史、提取所需记录、回到当前状态，并按账号有条件合并。未有此授权和计划时停止，不执行restore。
4. 恢复结果需检查目标账号的笔记、标记、答题、翻译草稿、清单和复习计划；其他账号与新记录不能倒退。不要把应用发布成功写成历史数据恢复成功。

本次没有查看或回滚生产数据库，也没有索取正式凭据；真实数据是否可恢复仍取决于现存副本和可用恢复点。
